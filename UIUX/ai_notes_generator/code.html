01

Executive Architectural TL;DR

In distributed Indian fintech workflows—such as handling high-throughput asynchronous webhooks from Razorpay, PhonePe, or NPCI UPI switches—at-least-once network guarantees will inevitably create duplicate requests. Achieving strict idempotency without introducing catastrophic write lock contention requires a dual-tier persistence invariant.

Key Invariant #1

Natural vs Synthetic Keys

Never trust client-generated UUIDs solely. Pair vendor signature hashes with order references (x-razorpay-signature).

Key Invariant #2

Atomic Guard (SETNX)

Execute state reservation in Redis with TTL before hitting relational DB transactions to prevent thread exhaustion.

Key Invariant #3

Postgres Upsert Guard

Final layer defense relies on ON CONFLICT (idempotency_key) DO NOTHING with read committed isolation.

Critical Design Rule from Cohort Q&A

Always respond with HTTP 200 OK immediately once duplicate detection confirms the event is already in-flight or completed. If you return 5xx or 429 during duplicate detection, Razorpay will exponentially back off and retry, compounding queue pressure.

package webhook

import (
  "context"
  "fmt"
  "time"
  "github.com/redis/go-redis/v9"
)

// AcquireLock enforces atomic single-flight execution for vendor events
func AcquireLock(ctx context.Context, rdb *redis.Client, eventID string, ttl time.Duration) (bool, error) {
  key := fmt.Sprintf("lock:razorpay:event:%s", eventID)
  // SETNX: Atomic set if not exists
  ok, err := rdb.SetNX(ctx, key, "PROCESSING", ttl).Result()
  if err != nil {
    return false, fmt.Errorf("redis lock failure: %w", err)
  }
  return ok, nil
}
04

Production Pitfalls & Hard Truths

warning Anti-Pattern: Zombie Key Deadlocks with Non-Expiring Keys

During live production surges (e.g. Flash Sales, Flipkart Big Billion Days, or festival cohort enrollments), services may panic or experience OOM kills after acquiring a lock but before committing DB records. If your Redis lock does not feature a mathematically bound TTL, the event ID remains locked permanently, preventing legitimate automatic retries from ever settling the transaction.

The Gold Standard Fix:

Always set TTL to exactly 3x Max-SLA of your slowest downstream write. Include a Lua script release check that compares an execution nonce so workers do not delete subsequent requests' locks.

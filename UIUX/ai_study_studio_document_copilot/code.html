01. Distributed Idempotency Invariants

In real-world payment and event architectures, network faults cause duplicate POST requests. Idempotency guarantees that multiple identical requests produce the identical side effect on state as a single invocation.

  • verified Client-Generated Keys: Use v4 UUID generated at client boundary (`Idempotency-Key: b7f90c42-...`), never derived solely from payload hashes to allow intentional repeated checkouts.
  • verified Two-Phase State Machine: Register state as `PROCESSING` with a lease TTL before firing external RPCs. Transition to `RESOLVED` caching the exact response body.

Atomic SETNX with 120-second recovery TTL acquired, err := rdb.SetNX(ctx, lockKey, "LOCKED_PROCESSING", 120*time.Second).Result() if err != nil { return nil, fmt.Errorf("redis cluster unreachable: %w", err) } if !acquired { // 2. warning
Tier-1 Production Pitfall: The Zombie Key Deadlock

Never register an idempotency record without a hard TTL in Redis or an expiration timestamp in PostgreSQL. If the process terminates abnormally (e.g., OOMKilled by Kubernetes) during payment processing, a key without TTL stays locked permanently, preventing clients from ever safely re-submitting.

Debugging Drill • Concurrency Race Condition

Identify the race condition in this naive SQL idempotency check under high concurrent load:

-- Vulnerable implementation without atomic upsert SELECT status FROM idempotency_keys WHERE key = 'req_8829'; -- [GAP: Concurrent threads both see 0 records here] INSERT INTO idempotency_keys (key, status) VALUES ('req_8829', 'PENDING');
verified Production Fix: PostgreSQL ON CONFLICT DO NOTHING
INSERT INTO idempotency_keys (key, status, created_at) VALUES ('req_8829', 'PENDING', NOW()) ON CONFLICT (key) DO NOTHING; -- Check row_count(); if 0, key already claimed atomically.
